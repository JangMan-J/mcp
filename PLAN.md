# MCP client: implementation plan

Build a new client and host-facing TypeScript library in this repository from official MCP specifications. It is not a fork of an SDK, `pi-mcp-ext`, or Pi. Writers derive wire behavior and tests from pinned specifications, schemas and standards; do not use existing MCP implementations as implementation references. Official conformance runners may exercise the implementation as black boxes. General-purpose JSON Schema, crypto, HTTP and UI libraries are not MCP implementations; justify and pin any such dependency. A TypeScript library lets both Pi hosts load it in-process later without a daemon or FFI. The protocol library itself does not import Pi.

## Scope

- Client/host side only. A synthetic server used by tests is not a shipped server or proxy.
- Primary profile: [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), tag `5f5440bb26a62e2cf3440b92da5a667efa03b267`. Implement every applicable client requirement and every active core optional that can be implemented without contradicting a guarantee. Record role, conditions, default, acceptance test and disposition for every requirement; no vacuous capability flags.
- Six-month lookback anchored to 2026-11-19: earliest eligible compatibility revision is 2026-05-19. `2025-11-25` is outside it; ship no initialize-era fallback, GET/DELETE session machinery or legacy resumable SSE. Surface an actionable unsupported-version diagnostic. Don't carry deprecated roots, sampling, MCP logging, dynamic client registration, or HTTP+SSE. Preserve active transport progress, stderr diagnostics and OpenTelemetry separately. Confirm the exact deprecated list against the dated revision.
- Non-core optionals: inventory each official Stable/Beta extension (Tasks, Skills, Client Credentials, Enterprise-Managed Authorization, Apps, Server Cards), plus SEP-3415 Events by explicit request. Implement them independently and opt-in, including host-neutral adapters where a browser, identity provider or inbound listener is needed. Include webhook delivery in the Events plan, isolated from the local client runtime. For other Experimental items, inventory and check whether there is a pinned specification and an independent client contract; no silent omission or automatic adoption of unbounded drafts. Unsettled or incompatible contracts get a named disposition, not a pretend capability.
- Start with the wiki at `~/vaults/JangsWiki/Wiki/mcp/index.md`; open individual pages. Its Nov. 16 mirror includes SEP-3415 at `4165cc2e580a`, behind the upstream PR head `60b15c16f2e7265ea34ac51099dc5be62f734692` checked Nov. 19. Pin each authoritative source separately; resolve wiki ↔ dated-tag differences before encoding a test. Events stays draft-labeled and off by default.

## Modules and order

1. **Contracts and fixtures.** Derive requirement IDs from normative sections; pin extension revisions and differentiate required, active optional, conditional, deprecated, excluded, and unresolved. Define a small client request/stream interface and normalized outcomes. Keep JSON-RPC faults, transport failures, application `isError`, MRTR interim results and optional Tasks outcomes distinct. Store scripted exchange expectations separately from implementation.
2. **Core.** After shared interfaces freeze, build disjoint lanes for wire/lifecycle; stdio; HTTP/SSE/headers; operation surfaces and JSON Schema/content; authorization and host consent; then MRTR/subscriptions/cache where they share state. Core covers discovery and version metadata, tools, prompts, resources, completion and pagination; negotiated change subscriptions, progress and cancel; form/URL elicitation and state-only MRTR; cache metadata and bounded private/public caching; OAuth + configured bearer credentials; telemetry. Keep per-request state and cancellation separate from the lifetime of a server transport. An ambiguous interrupted write must never become an unreported duplicate side effect: implement the binding's exact recovery semantics, surface uncertainty to callers and test it.
3. **Optionals.** Independent packages/modules behind explicit registration and advertised only with working capabilities. Tasks and Events should use the same stream primitives without teaching core about their methods. Use narrow consent, browser/identity, and persistence interfaces solely where specifications require them. No UI shell, background agent wake or user workflow policy in core. Verify a capability can be removed without changing core outcomes.
4. **Spec gate.** In a fresh process with no Pi packages: run the requirement-linked fixtures and relevant published client conformance scenarios. Where no official runner covers a clause, retain the spec-derived fixture and say so. Exercise simultaneous requests, cancellation and closure, permissions/consent, auth continuity, cache separation, subscriptions, partial transport failure, and result/error shapes. Release claims require a disposition for every row and a passing check for every implemented row. Inapplicable server requirements stay explicitly out-of-scope. An extension draft is not core conformance evidence.
5. **Pi adapters, after the spec gate.** First target the user's fork, not upstream standing in for it. Record both the installed fork build (`next-7d80b45f62f8` at planning) and the checked-out fork revision (`e903c27bb`) separately; verify the adapter against a pinned target. Coding Agent adapter owns session registration, `/mcp`, trust/exposure, native resource aliases, `tool_search`, `reachesTools`, names, raw structured codemode results vs bounded model output, nested permission/cancel lifecycle, branch/fork/resume, and migration rollback. Reuse the host's codemode sandbox, not its MCP implementation. Treat standalone `pi mcp` as a separate cutover only if an extension cannot replace it. Durable adapter is separate: verify commit-before-wake, replay of completed results, interruption with unresolved external side effects, persisted remote handles, and replay cursors. Do not claim exactly-once side effects from local checkpoints. No changes to the fork, active config or existing extension before this gate and an explicit cutover plan.

## Work assignment

Wave 0 is documentation and conformance design. Each lane owns one file under `docs/conformance/`; no shared edits. Every row gives a spec anchor, role/strength/condition, one observable check and any open question. The director reconciles shared decisions before implementation starts.

| Lane | Deliverable |
|---|---|
| Wire | `wire.md`: envelopes, versions, stdio/HTTP/SSE, routing, cancellation and progress |
| Operations | `operations.md`: discovery, lists, schemas/content, MRTR, elicitation, subscriptions, caching |
| Authorization | `authorization.md`: core authorization and host consent, auth extension seams and checks |
| Extensions | `extensions.md`: remaining extensions, SEP-3415 pin and three delivery modes, acceptance and fallback |

Wave 1 begins with the shared interface and fixture runner, then assigns four independent implementation slices with explicit file paths and checks. Wave 2 adds remaining modules and optionals. Wave 3 starts only after the spec gate and contains two host adapters. No deployment, remote repository creation, or publication in Wave 0.
