# Authorization conformance rows

Wave 0 lane file for **Authorization** (`AUTH-*`, `CONSENT-*`, `EXT-cc-*`, `EXT-ema-*`). Derived from IMPLEMENTATION_PLAN.md sections 10, 12.3, 12.4 and 16.1. Documentation only: no MCP implementation, no edits outside this file.

## How to read the table

- **Anchor** is `page#heading`, relative to the wiki root `~/vaults/JangsWiki/Wiki/mcp/` (every page and heading was checked to exist). Three non-wiki forms: `ext-auth:<path>#<heading>` (the extension spec in `modelcontextprotocol/ext-auth`), `rfc9728#<section>` (standard input, not an MCP implementation, N1/N4), and `#(intro, before first heading)` / `#(whole document)` where the source has no heading.
- **Role**: `C` client, `S` server, `B` both, `host` a duty the library hands to the embedding host through a port. **Strength** is the source keyword, or `derived` when no keyword exists in the source.
- **Acceptance check** is one observable: a fixture id (`auth/*`, `consent/*`, `ext/cc/*`, `ext/ema/*`, in the synthetic server plus synthetic AS/IdP, plan 10.10 and 13), a named unit vector, a doc check, or `none (server role)`. Names not present in plan 10.10 are new and listed in the changelog.
- **Open question** uses `Q<n>`. Q9, Q12, Q15 exist in plan 17.3. Q31 to Q37 are proposed here; the director registers them in `DECISIONS.md` (definitions below).
- **Pin values** live in [PINS.md](PINS.md), which the director owns. This file does not restate them, except the observed evidence below that the director needs to reconcile.
- Wiki mirror vs dated tag: the four core authorization pages are `same` (see Evidence). The two extension pages are `semantic` and their rows carry the difference.

### E4. AUTH-PRM-3 verified against RFC 9728 s3.3 (closes Q12's "source" half)
RFC 9728 s3.3 (text fetched from rfc-editor.org): "The resource value returned MUST be identical to the protected resource's resource identifier value into which the well-known URI path suffix was inserted to create the URL used to retrieve the metadata. If these values are not identical, the data contained in the response MUST NOT be used." For metadata obtained through the `WWW-Authenticate` `resource_metadata` URL, `resource` MUST be identical to the URL the client used to make the request to the resource server. s7.3 repeats this and adds a TLS certificate check (new row AUTH-PRM-4). The MCP pages only say clients "MUST use" PRM and consult RFC 9728; they do not restate the check. Plan 10.2 said "must match the canonical URI" and "derived"; correct it to the two cases above. Disposition stays `required`, strength `MUST` from the RFC, source external.

### E5. Plan deltas found while anchoring (director to confirm)
- AUTH-BIND-2: the plan says "AS changed: discard registration and tokens and redo". REG#Authorization Server Binding says pre-registered credentials that no longer match the AS: SHOULD surface an error; CIMD client IDs are portable, no re-registration (Q37).
- AUTH-URL-1: the plan says browser URLs are https only. SBP allows `http` for loopback in development. The project default is stricter than the spec (recorded in the row default; D6).
